# 📚 Лекция 1: Основы Git, конфигурация и ветвление

## 🎯 Цель лекции

Научиться настраивать Git, понимать жизненный цикл файлов (статус, индексация, коммит) и уверенно управлять ветками.

-----

## 🏗 Часть 1: Терминология и Первоначальная настройка

Перед началом работы важно понять основные термины, которые мы будем использовать.

### 🔑 Основные термины

  * **Репозиторий (Repo):** Хранилище вашего кода и всей истории его изменений. Физически это папка `.git` в корне вашего проекта.
  * **Коммит (Commit):** Фиксация изменений. Это "снэпшот" (слепок) состояния всех файлов проекта в конкретный момент времени.
  * **Staging Area (Индекс/Сцена):** Промежуточная зона, куда вы добавляете файлы перед тем, как сделать коммит. Это позволяет выбрать, какие именно изменения войдут в следующий снимок.
  * **Ветка (Branch):** Независимая линия разработки.
  * **HEAD:** Указатель на текущую ветку и последний коммит, с которым вы сейчас работаете.

### ⚙️ Конфигурация (Global Setup)

Git должен знать, кто вносит изменения. Эти данные будут записаны в каждый ваш коммит.

**1. Установка имени пользователя**
Эта команда задает имя, которое будет отображаться в истории изменений.

```bash
git config --global user.name "Your Name"
```

**2. Установка email**
Email должен совпадать с тем, что вы используете на GitHub/GitLab, чтобы сервис мог связать коммиты с вашим аккаунтом.

```bash
git config --global user.email "your_email@example.com"
```

**3. Проверка настроек**
Чтобы убедиться, что всё сохранилось корректно:

```bash
git config --list
```

> **Терминал выдаст:**
> user.name=Your Name
> user.email=your\_email@example.com
> ... (другие настройки)

## 🚀 Часть 2: Инициализация и Жизненный цикл файлов

### Инициализация репозитория

Превращает текущую папку в Git-репозиторий.

```bash
git init
```

> **Терминал выдаст:**
> Initialized empty Git repository in /Users/username/project/.git/

### 🔍 Git Status: Ваш лучший друг

Эта команда показывает, что происходит в репозитории прямо сейчас: какие файлы изменены, какие добавлены в индекс, а какие Git вообще не видит.

**Базовый статус:**

```bash
git status
```

**Короткий формат (для опытных):**
Флаг `-s` (short) показывает статус в компактном виде.

```bash
git status -s
```

> **Терминал выдаст (пример):**
> M file.txt   (Modified - изменен)
> ?? new.txt    (Untracked - не отслеживается)
> A  added.txt  (Added - добавлен в индекс)

### Добавление в индекс (Staging)

Git не сохраняет изменения автоматически. Сначала нужно сказать ему: "Я хочу, чтобы этот файл вошел в следующий коммит".

Добавить конкретный файл:

```bash
git add filename.txt
```

Добавить **все** текущие изменения (новые и измененные файлы) в текущей папке:

```bash
git add .
```

## 💾 Часть 3: Коммиты (Фиксация изменений)

Коммит создает точку сохранения.

### 1\. Стандартный коммит

Ключ `-m` (message) позволяет сразу написать сообщение к коммиту. Без него Git откроет текстовый редактор (обычно Vim или Nano).

```bash
git commit -m "Первый коммит: добавлена структура проекта"
```

> **Терминал выдаст:**
> [master (root-commit) 8f3a1b2] Первый коммит: добавлена структура проекта
> 1 file changed, 1 insertion(+)
> create mode 100644 readme.md

### 2\. Коммит "всё включено" (для ленивых)

Ключ `-a` (all) автоматически делает `git add` для всех **уже отслеживаемых** файлов (тех, что были в репозитории раньше) и сразу делает коммит.
*Внимание: Это не сработает для абсолютно новых файлов (Untracked).*

Можно комбинировать ключи `-a` и `-m`:

```bash
git commit -am "Быстрое исправление бага"
```

### 3\. Исправление последнего коммита (Amend)

Если вы сделали коммит, но забыли добавить файл или ошиблись в комментарии, не нужно делать новый коммит. Ключ `--amend` позволяет переписать **последний** коммит.

```bash
git commit --amend -m "Исправленное сообщение коммита"
```

*Это изменит хеш (ID) последнего коммита.*

## 🌳 Часть 4: Работа с ветками (Branching)

Ветки позволяют работать над новыми функциями, не ломая основной код.

### Просмотр веток

Показывает список веток. Звездочка `*` указывает на текущую ветку.

```bash
git branch
```

> **Терминал выдаст:**
>
>   * master
>     feature-login

Чтобы увидеть все ветки (включая удаленные на сервере), используйте ключ `-a`:

```bash
git branch -a
```

### Создание новой ветки

Создает ветку, но **не переключает** на неё.

```bash
git branch feature-new-design
```

### Переключение между ветками

Для перехода в другую ветку.

```bash
git checkout feature-new-design
```

*Или более современная команда (появилась в Git 2.23):*

```bash
git switch feature-new-design
```

> **Терминал выдаст:**
> Switched to branch 'feature-new-design'

### Создание и переключение одной командой

Самая частая операция. Создает ветку и сразу переносит вас в неё.
Ключ `-b` (branch).

```bash
git checkout -b bugfix-header
```

*Или современный аналог с ключом `-c` (create):*

```bash
git switch -c bugfix-header
```

### Слияние веток (Merge)

Представьте, что вы закончили работу в ветке `bugfix-header` и хотите влить эти изменения в главную ветку `master`.

1.  Сначала перейдите в ветку, **в которую** хотите влить изменения:

<!-- end list -->

```bash
git switch master
```

2.  Выполните команду merge с указанием ветки, **откуда** берем изменения:

<!-- end list -->

```bash
git merge bugfix-header
```

> **Терминал выдаст:**
> Updating 34ac2..89df1
> Fast-forward
> header.css | 2 ++
> 1 file changed, 2 insertions(+)

### Удаление веток

Когда ветка слита и больше не нужна, её стоит удалить для порядка.

Безопасное удаление (Git предупредит, если ветка не была слита):

```bash
git branch -d bugfix-header
```

Принудительное удаление (Force delete), если нужно удалить ветку с экспериментами, которые решили не сохранять:

```bash
git branch -D bugfix-header
```

## 📝 Итог первой лекции

Вы теперь умеете:

1.  Представляться Гиту (`config`).
2.  Создавать репозиторий (`init`).
3.  Проверять состояние (`status -s`).
4.  Сохранять изменения (`add`, `commit -m`, `commit -am`, `commit --amend`).
5.  Работать в параллельных потоках (`branch`, `checkout -b`, `merge`).

**Во второй лекции мы разберем:**

  * Работу с историей (`log`).
  * Отмену изменений и перемещение во времени (`reset`, `revert`, `checkout` файлов).
  * Удаленные репозитории (`remote`, `push`, `pull`, `clone`).
  * Стратегии ветвления (Git Flow, GitHub Flow).

# 📚 Лекция 2: Файлы проекта, История и Откат изменений

## 🎯 Цель лекции

Научиться вести проект профессионально (игнорирование мусора, документация), читать историю изменений как карту и исправлять ошибки, откатываясь назад.

-----

## 📄 Часть 1: Важные файлы репозитория

В любом профессиональном проекте есть файлы, которые не являются кодом программы, но критически важны для Git и команды.

### 1\. `.gitignore` (Что игнорируем?)

**Зачем это:** В папке проекта часто появляется мусор: временные файлы, логи, папки с зависимостями (например, `node_modules` весит сотни мегабайт), ключи API или настройки редактора. Если их закоммитить, репозиторий распухнет, а коллеги будут злиться.
Этот файл говорит Гиту: *"Даже не предлагай мне добавить эти файлы в индекс"*.

**Как создать:** Просто создайте файл с именем `.gitignore` в корне проекта.

**Пример содержимого:**

```text
# Игнорировать папку с зависимостями
node_modules/
dist/

# Игнорировать файлы настроек системы
.DS_Store

# Игнорировать файлы с секретами (ОЧЕНЬ ВАЖНО)
.env
secret_key.txt
```

### 2\. `README.md` (Лицо проекта)

**Зачем это:** Это первое, что видит человек, открывая ваш репозиторий на GitHub. Если этого файла нет, проект считается "дурным тоном". В нем описывают: что делает проект, как его запустить и как им пользоваться.
Формат `.md` означает Markdown — простой язык разметки текста.

### 3\. `CHANGELOG.md` (История для людей)

**Зачем это:** `git log` показывает технические изменения кода. А `CHANGELOG` — это файл для пользователей и менеджеров. Там пишут, что изменилось в версии программы понятным языком.

**Пример структуры:**

```markdown
## [1.0.1] - 2023-10-05
### Добавлено
- Кнопка "Купить" на главной странице.
### Исправлено
- Ошибка при входе через Google.
```

## 📜 Часть 2: Навигация по истории (`git log`)

**Зачем это:** Чтобы понять, кто, когда и что сломал (или починил).

### Базовый просмотр

Выводит список коммитов с автором, датой и сообщением.

```bash
git log
```

*Выход из режима просмотра: клавиша `q`.*

### Визуализация дерева (ASCII-графика)

Самая полезная вариация команды. Она рисует дерево ветвления прямо в терминале.

  * `--oneline`: сокращает информацию до хеша и названия.
  * `--graph`: рисует линии ветвления.
  * `--all`: показывает все ветки, а не только текущую.

<!-- end list -->

```bash
git log --oneline --graph --all
```

> **Что выдает терминал (пример):**
>
> ```text
> * 8f3a1b2 (HEAD -> feature-login) Добавлена валидация email
> * 4c2d1e5 Создана форма входа
> | * 9b2c1d3 (master) Исправлен баг в хедере
> |/
> * 7a1b2c3 Первый коммит: структура проекта
> ```

*Здесь видно, что ветка `feature-login` ушла вперед от `master`, но в `master` тоже было одно независимое изменение.*

## ⏳ Часть 3: Машина времени (Откат изменений)

Это самая сложная, но важная часть. Ошибки случаются, и Git дает три способа их исправить: `Checkout` (Restore), `Revert` и `Reset`.

### Ситуация 1: "Я натворил дел в файле, но еще не сделал коммит"

Вы испортили файл `script.js` и хотите вернуть его к состоянию последнего коммита.

**Команда:**

```bash
git checkout filename
# или в новых версиях Git:
git restore filename
```

*Файл мгновенно вернется к исходному виду. Осторожно: ваши несохраненные правки исчезнут навсегда\!*

### Ситуация 2: "Я уже сделал коммит, но он ошибочный (Безопасный откат)"

Вы закоммитили баг. Вы хотите отменить этот коммит, но **сохранить историю**, чтобы все видели, что была ошибка и её исправили.

**Команда `revert`:**
Создает **новый** коммит, который делает всё наоборот (удаляет добавленное, добавляет удаленное).

```bash
git revert <hash_commit>
```

*Где `<hash_commit>` — это ID коммита (например, `8f3a1b2`), который можно узнать через `git log`.*

> **ASCII-дерево после revert:**
>
> ```text
> * a1b2c3d Revert "Добавлена сломанная кнопка"  <-- Новый коммит
> * 8f3a1b2 Добавлена сломанная кнопка           <-- Ошибочный коммит (остался в истории)
> * 7a1b2c3 Начало работы
> ```

### Ситуация 3: "Удалить последние коммиты, как будто их не было (Опасный откат)"

Вы работали локально, наделали ерунды и хотите просто вернуться в прошлое, стерев последние события.

**Команда `reset`:**
Перемещает указатель ветки (HEAD) назад.

1.  **Soft Reset (Мягкий):**
    Удаляет коммиты из истории, но **оставляет изменения в файлах** (в Staging area). Полезно, если вы хотите склеить 3 мелких коммита в один.

    ```bash
    git reset --soft HEAD~1
    ```

    *(HEAD\~1 означает "на 1 коммит назад").*

2.  **Hard Reset (Жесткий):**
    Удаляет коммиты и **уничтожает изменения в файлах**. Всё, что было сделано после точки возврата, исчезнет.

    ```bash
    git reset --hard HEAD~1
    ```

> **ASCII-дерево после reset --hard:**
> *Было:*
>
> ```text
> * 8f3a1b2 (HEAD) Плохой коммит
> * 7a1b2c3 Хороший коммит
> ```
>
> *Стало:*
>
> ```text
> * 7a1b2c3 (HEAD) Хороший коммит
> ```

*(Коммит `8f3a1b2` исчез из истории).*

# 📚 Лекция 3: Удаленные репозитории и Git Flow

## 🎯 Цель лекции

Научиться работать с GitHub/GitLab (синхронизация) и понять, как организовать работу в команде, чтобы не мешать друг другу (стратегии ветвления).

-----

## ☁️ Часть 1: Работа с удаленным сервером (Remote)

Ваш код на компьютере — это "Локальный репозиторий". Код на GitHub — это "Удаленный репозиторий" (Remote).

### 1\. Клонирование (`clone`)

**Зачем это:** Чтобы скачать чужой проект или свой проект с сервера на новый компьютер. Эта команда сама делает `git init`, создает папку и скачивает всю историю.

```bash
git clone https://github.com/user/project.git
```

### 2\. Привязка к серверу (`remote add`)

**Зачем это:** Если вы создали проект у себя локально и хотите "подружить" его с пустым репозиторием на GitHub.

```bash
git remote add origin https://github.com/user/project.git
```

  * `origin` — это стандартное имя для основного удаленного сервера (псевдоним ссылки).

### 3\. Отправка изменений (`push`)

**Зачем это:** Загрузить ваши новые локальные коммиты на сервер.

При первой отправке новой ветки нужно использовать ключ `-u` (upstream), чтобы связать локальную ветку с веткой на сервере:

```bash
git push -u origin master
```

В дальнейшем достаточно просто писать:

```bash
git push
```

### 4\. Получение изменений (`pull`)

**Зачем это:** Скачать новые коммиты, которые сделали ваши коллеги, и влить их в вашу папку.
Это комбинация двух команд: `git fetch` (скачать данные) + `git merge` (влить их).

```bash
git pull
```

## 🔀 Часть 2: Workflows (Стратегии ветвления)

Как организовать ветки, когда над проектом работают 5 человек? Есть две популярные модели.

### 1\. GitHub Flow (Простой вариант)

Идеально для небольших проектов и веба.

  * Есть одна вечная ветка **Master/Main**. Она всегда рабочая.
  * Для любой задачи создается новая ветка от Master.
  * Работа сделана -\> Pull Request -\> Тесты -\> Слияние в Master.

> **ASCII-схема GitHub Flow:**
>
> ```text
>       (start feature)            (merge)
>          /--------------------------\
> *-------*--------------------------*-------> (Master/Main)
>         \                          /
>          *---*---* (Feature-branch)
> ```

### 2\. Git Flow (Классический/Сложный вариант)

Используется в крупных проектах со строгими релизами.

**Основные роли веток:**

1.  **Main (Master):** Только чистый код продакшна (версии 1.0, 1.1).
2.  **Develop:** Основная ветка разработки. Сюда сливаются все задачи.
3.  **Feature:** Ветки для конкретных задач. Ответвляются от Develop, вливаются в Develop.
4.  **Release:** Подготовка к выпуску (правка багов перед релизом).
5.  **Hotfix:** Срочные исправления багов на продакшне.

> **ASCII-схема Git Flow:**
>
> ```text
> (Hotfix branch)
>   /-----\
>  /       \    (v1.0)           (v1.1)
> *---------*-----*-----------------*---------> (Main)
>            \   / \               /
>             \ /   \ (Release)   /
>              *-----*-----------*------------> (Develop)
>              \                 /
>               \               /
>                *-----*-------* (Feature 1)
> ```
